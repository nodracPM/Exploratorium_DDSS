# Object Popup Feature And Build Workflow

## Summary

This change adds object-level popups to the lattice UI. After updating the ODS source, running the database import, and rebuilding the site, clicking an object label now shows:

- label
- description
- year
- reference

The implementation was designed to mirror the existing attribute popup flow while keeping object metadata in a dedicated database view and a dedicated diagram catalog file.

## What Was Added

### 1. New database view: `v_objects`

Added in [db/ddl.sql](/home/pmcc/Desktop/social service/Exploratorium_MMSS/db/ddl.sql).

Purpose:

- provide a clean object-facing dataset similar to `v_attributes`
- expose object detail fields already stored in the schema
- decouple frontend exports from lower-level joins

Columns exposed:

- `Lang`
- `Context`
- `Code`
- `Label`
- `Year`
- `Description`
- `Reference`

This view is now the canonical source for object popup metadata during site generation.

### 2. New diagram catalog file: `obj_desc.csv`

Generated by [scripts/gen_diagram_catalogs.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/gen_diagram_catalogs.sh).

For each context/language diagram directory, the build now exports:

- `attr_desc.csv` for attributes
- `attr_class_desc.csv` for attribute class legend data
- `obj_desc.csv` for object popup data

`obj_desc.csv` contains:

- `Code`
- `Label`
- `Description`
- `Year`
- `Reference`

This file is the frontend input for object click popups.

### 3. Object click popup support in the frontend

Implemented in [site/lib/reticulo.js](/home/pmcc/Desktop/social service/Exploratorium_MMSS/site/lib/reticulo.js).

New behavior:

- the frontend now loads `obj_desc.csv`
- object metadata is stored by object code
- every object label rendered in the lattice receives a click handler
- clicking an object opens the existing infobox
- the infobox shows:
  - label as heading
  - description
  - year
  - reference
- the popup content is shown without prefixed field labels such as `Description:`
- object labels now use the same pointer cursor behavior as clickable attribute labels
- the cursor styling is enforced with a selector that overrides the generic `.node * { cursor: grab; }` rule

The object popup uses the same infobox system already used by attributes, so no new page template structure was required.

### 4. Full lattice regeneration during `build.sh`

Updated in [scripts/build.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/build.sh).

The build now runs:

```bash
scripts/gen_lattices.sh -f "$DBDSN"
```

instead of the non-forced version.

Reason:

- object metadata edits can change visible object labels even when object-attribute assignments do not change
- the previous incremental lattice generation strategy was centered on `object_attribute` diffs
- forcing lattice regeneration ensures label changes made in the ODS are reflected in `lattice.json`

This makes the workflow much more reliable for content editing.

## Workflow Explanation

### Step 1. Edit the ODS source

You update the object-related fields in the spreadsheet, including:

- object label
- object description
- object year
- object reference

The relevant import-side columns are:

- `object_label_en`
- `object_label_es`
- `object_desc_en`
- `object_desc_es`
- `year`
- `reference`

### Step 2. Run `ods2db.sh`

Script:

- [scripts/ods2db.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/ods2db.sh)

What it does:

1. calls [scripts/ods2csv.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/ods2csv.sh) to extract sheet data from the ODS into temporary CSV and PSV files
2. calls [scripts/csv2sql.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/csv2sql.sh) to convert those flat files into SQL inserts
3. creates a new SQLite database by applying [db/ddl.sql](/home/pmcc/Desktop/social service/Exploratorium_MMSS/db/ddl.sql)
4. loads the generated data SQL into that database

Why this matters here:

- `csv2sql.sh` already maps ODS object metadata into:
  - `object.reference`
  - `object.year`
  - `object_desc.desc`

So after `ods2db.sh`, the database contains the object popup data.

### Step 3. Run `build.sh`

Script:

- [scripts/build.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/build.sh)

What it does:

1. runs [scripts/gen_diagram_catalogs.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/gen_diagram_catalogs.sh)
2. runs [scripts/gen_lattices.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/gen_lattices.sh) with `-f`
3. runs [scripts/gen_pages.sh](/home/pmcc/Desktop/social service/Exploratorium_MMSS/scripts/gen_pages.sh)

Why each step matters:

- `gen_diagram_catalogs.sh`
  - exports `attr_desc.csv`
  - exports `attr_class_desc.csv`
  - exports `obj_desc.csv`
- `gen_lattices.sh -f`
  - regenerates every `lattice.json`
  - makes sure object label changes are visible in the diagrams
- `gen_pages.sh`
  - regenerates the page HTML around the diagram assets

### Step 4. Open the generated site

When a diagram page loads:

1. [site/lib/reticulo.js](/home/pmcc/Desktop/social service/Exploratorium_MMSS/site/lib/reticulo.js) loads:
   - `attr_desc.csv`
   - `attr_class_desc.csv`
   - `obj_desc.csv`
   - `lattice.json`
   - `pos.json`
2. attribute labels get the existing attribute click behavior
3. object labels now also get a click handler
4. clicking an object looks up its code in `obj_desc.csv`
5. the infobox is populated with label, description, year, and reference

## Data Flow

The full object popup path is now:

1. ODS cells
2. `ods2csv.sh`
3. `csv2sql.sh`
4. SQLite tables `object` and `object_desc`
5. `v_objects`
6. `gen_diagram_catalogs.sh`
7. `obj_desc.csv`
8. `reticulo.js`
9. object click popup in the browser

## Design Rationale

### Why create `v_objects`?

Because it gives object metadata a stable export surface similar to `v_attributes`.

Benefits:

- simpler SQL in the catalog generator
- clearer separation of concerns
- easier future maintenance if object fields grow

### Why not reuse `v_object_context`?

`v_object_context` is useful for lightweight context listings, but the popup feature needs a purpose-built detail view aligned with frontend requirements.

### Why force lattice regeneration during build?

Without it, object metadata edits could update popup data while leaving visible object labels stale in `lattice.json`.

The forced regeneration trades some speed for much better correctness and predictability.

## Expected Usage

Recommended workflow:

```bash
scripts/ods2db.sh -f your-data.ods db/test.db
scripts/build.sh db/test.db
```

After that, open the generated site and click an object label in any diagram.

Important:

- the existing checked-in database file must be regenerated before the new feature can work
- if you run `build.sh` against an older database that does not include the new schema objects, the object catalog export will fail because `v_objects` will not exist

If you want the default build path to work without arguments, regenerate the default database file itself:

```bash
scripts/ods2db.sh -f your-data.ods db/exploratorium.db
scripts/build.sh
```

## Validation Notes

The implementation was structured so that:

- the database exposes object popup data through `v_objects`
- the build emits `obj_desc.csv`
- the frontend reads and uses that file for object clicks
- the build forces fresh lattices so content edits are reflected visually

If object popups are missing after a rebuild, the first things to verify are:

- the ODS contains values in the object metadata columns
- `obj_desc.csv` was generated in the relevant diagram directory
- the rebuilt `lattice.json` contains the expected objects for that context
